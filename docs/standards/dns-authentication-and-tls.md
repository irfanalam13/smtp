# DNS, authentication, and transport security

## DNS routing

The transport resolver follows RFC 5321 §5 with RFC 1034/1035 DNS behavior, RFC 2181 clarifications, RFC 2308 negative caching, and RFC 7505 Null MX:

1. Query MX for the recipient domain.
2. Treat a valid Null MX as an explicit no-service result, not a fallback to A/AAAA.
3. Sort MX hosts by preference and randomize equal-preference candidates as appropriate.
4. Resolve A/AAAA for each selected MX host; apply address safety filtering before connect.
5. Apply the RFC-defined fallback only when MX is absent, not when DNS returns an explicit negative or Null MX result.
6. Classify timeout/SERVFAIL-like temporary resolver failures separately from NXDOMAIN/permanent routing failures.
7. Respect TTL and negative-cache guidance while bounding local cache duration and refresh.

DNS answers are untrusted input. Resolver timeouts, maximum response sizes, CNAME/address behavior, IDNA conversion, DNSSEC status, and private-address filtering are implementation/test concerns. DANE requires validated DNSSEC/TLSA data and is not enabled by merely resolving MX.

## SPF, DKIM, and DMARC

| Capability             | Standard                                      | Initial platform responsibility                                                                                                                                                                                               |
| ---------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SPF                    | RFC 7208                                      | Publish customer guidance/verification; enforce DNS lookup limits and distinguish pass, fail, softfail, neutral, none, temperror, and permerror when validating inbound or diagnostics. SPF does not prove message integrity. |
| DKIM                   | RFC 6376, RFC 8301, RFC 8463                  | Generate and rotate tenant signing keys, sign approved outbound messages, and verify inbound signatures only after key storage and canonicalization tests. Weak algorithms and keys are not accepted for new signing.         |
| DMARC                  | RFC 9989, RFC 9990, RFC 9991; legacy RFC 7489 | Discover policy, evaluate SPF/DKIM alignment against the Author Domain, expose disposition/reporting results, and avoid treating policy as proof of delivery.                                                                 |
| Authentication-Results | RFC 8601                                      | Add only trusted results generated by the platform; strip or quarantine untrusted customer-supplied claims at a trust boundary.                                                                                               |
| ARC                    | RFC 8617 Experimental                         | Optional future forwarding signal; no launch dependency or trust decision based solely on ARC.                                                                                                                                |

The current DMARC reference is RFC 9989 and its reporting companions RFC 9990/9991, verified as published Standards Track documents in May 2026. RFC 7489 remains relevant for legacy records and deployed behavior but is obsolete as the sole normative reference.

## TLS and SMTP transport

- Use a maintained TLS implementation with TLS 1.2/1.3 policy selected by compatibility and current security review; prohibit TLS 1.0/1.1 per RFC 8996.
- Client-to-platform submission requires protected authentication; STARTTLS is not a substitute for authorization.
- For outbound SMTP, opportunistic STARTTLS is distinct from policy-required TLS. An advertised TLS handshake that fails under a required policy is a delivery failure, not a silent plaintext fallback.
- Validate the certificate for the remote SMTP hostname when certificate validation is selected. Preserve the MX hostname even when connecting to a validated address.
- MTA-STS (RFC 8461), TLS reporting (RFC 8460), DANE (RFC 7672), and REQUIRETLS (RFC 8689) are future/optional profiles with separate policy storage and telemetry.
- TLS protects a transport hop. It does not provide end-to-end message confidentiality across every relay.

## SMTP AUTH and authorization

RFC 4954 defines the AUTH extension and SASL negotiation; it does not decide whether a principal may send for a tenant, domain, or address. The platform adds tenant/resource authorization after authentication. Supported mechanisms must be selected explicitly, require TLS where credentials could otherwise be exposed, reject repeated failures with bounded rate limits, and support rotation/revocation. RFC 7628 OAuth SASL is optional and cannot be inferred from generic OIDC support.
